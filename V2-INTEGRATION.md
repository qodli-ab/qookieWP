# WordPress v2 connection

## Operation

New installations default to v2. Presence of the existing `qookieqloud_domain_registered` option keeps upgrades on v1. Successful explicit pairing changes the persisted mode to v2. Disconnect never falls back to v1.

The Connect POST requires `manage_options` and a WordPress nonce. State, PKCE verifier, current user and session are retained server-side for 20 minutes. The callback is generated by `admin_url('admin-post.php')`, including the configured scheme, hostname, subdirectory and port. It uses WordPress's actionless `admin_post` hook, so the callback URL has no query parameters. An exchange requires matching state, session and user; the attempt is consumed before the remote request.

The existing QQ connect popup and `/api/v2/pairing/exchange` issue credentials. No new backend statistics controller is needed: `/api/v2/installation/dashboard` uses the existing statistics controller after private-key middleware has resolved the domain.

The private record is AES-256-GCM encrypted in a non-autoloaded WordPress option using the authentication salt and site URL. It is never emitted to HTML. Changing the URL or salt requires reconnecting; administrators should revoke old installation credentials in QQ when retiring an installation. Database copies do not automatically establish a connection at another URL.

Only the public key is attached to `/v2/consentLoader.js`. There is no short-token exchange during banner startup. Existing consent and cookie behavior remains in the shared v2 client. Public keys are not account authentication.

After connect, settings changes or disconnect, clear page/CDN caches. Disconnect revokes only the installation's private key. It cannot remove already cached HTML or revoke the domain's shared public key. Failed exchanges or failed revocations preserve the stored connection.

The backend permits the callback origin for the public banner. If WordPress admin and frontend use different origins, ensure the frontend origin is also allowed in QQ before enabling the banner. Local testing against a live domain shares its settings and statistics.

## Verification

Run `php tests/v2-integration.php` for offline security and lifecycle contract checks. These stub WordPress APIs and are not a browser/end-to-end WordPress test. Backend pairing and API tests run in the Laravel project with an in-memory SQLite database.

Before release, test a real WordPress installation: connect, cancel, rejected role, local callback, statistics, public/logged-in banner switches, cached pages, reconnect and disconnect. Confirm the private key never appears in page source or browser requests. Verify an existing v1 installation still loads its original banner before migration. No production deployment is performed by these checks.
